# 六接口胎温与前刹车中控设计变更

日期：2026-10-24。

状态：用户已选择功能并入六接口底板、触屏替代原小屏和设置按键、保留蜂鸣报警，并在核对 7B 中文资料后要求继续；以本文为增量计划依据。不代表新固件、接线、PCB 或硬件验证已经完成。

规划检查：独立审阅者已检查，结论为“没有重要遗漏”。用户原生执行选择保留；[增量实施计划](../plans/2026-10-24-six-port-tire-brake-central.md)已获用户“是请继续”确认，正在原生执行离线部分。计划包含新移植代码的时间/CRC健壮性修正，旧固件保留。

基线：离线软件 `0c29469`、7B 四接口结构说明及提交 `a647181`、现有 `brake_temp_alarm_display_12V_RS485` V1.6。本文替换旧规格中的“四接口”和“不包含刹车报警”边界；其余胎温协议与可靠性要求继续适用。旧独立刹车固件作为行为对照保留，集成功能在新方向实现。

## 1. 用户已确定的目标与范围

- 微雪 **ESP32-P4-WIFI6-Touch-LCD-7B** 完整显示套件，与一块 **六接口采集底板**装在同一外壳。
- 接口 1–4：胎温 FL/FR/RL/RR，成品 RS485 MLX90640；胎温页显示四幅完整 32×24 热图。
- 接口 5–6：前刹车 FL/FR，两只 RS485 红外刹车盘温度探头；不引入 MAX31856，不扩展为四轮刹车。
- 刹车采集、热模型、报警、蜂鸣、参数保存及 RaceChrono BLE 全部并入底板。原小 OLED 和 SET/UP/DOWN 设置按键不再作为集成装置的产品界面；芯片维护用 BOOT/RESET/烧录接口保留。
- 通过 7B 触屏切换胎温、刹车、设置页面；任何页面下所有采集、报警与 BLE 均持续运行。
- 保留无高度、无轮端电池、点火上电自动工作/断电关闭，以及原有各轮线束约束。刹车实际线束另行核准。

## 2. 方案比较与本次选择

| 方案 | 取舍与结论 |
| --- | --- |
| 保留独立旧刹车板，7B 只增加显示/远程设置 | 能沿用原整板，但增加独立板和连接；用户已选择功能并入底板 |
| 六接口底板集成胎温单元与独立刹车控制单元 | 共享整机外壳和显示，同时保持采集/报警任务独立；**用户选择此功能归属** |
| 全部采集、报警及 BLE 都放在显示 P4/C6 路径 | 需改变四胎温 BLE 身份和故障边界；本次不采用 |

下述 MCU、双总线、命令及设置交互是据此提出的工程基线，供本文审阅，不是用户已经逐项指定的细节。

## 3. 控制器与接口分工

| 部分 | 工程基线 |
| --- | --- |
| 7B 的 P4/原配 1024×600 屏与触摸 | 页面、报警状态呈现、设置入口和板间通信；不持有刹车报警逻辑 |
| 四个胎温 C3 单元 | 各自独立 RS485 全帧采集、八分区、RejsaRubberTrac BLE、热图 SPI 快照 |
| 第五个 C3：双路刹车控制单元 | 两前刹车采集、现有共用热模型/ALM、状态判断、蜂鸣器、NVS、N BrakeTemp BLE、屏幕状态与命令处理 |
| 六探头接口与供电 | 六支路标识和受保护供电；按实际探头核准针脚、线径、回流和防错插 |

六个插口不要求六个 MCU。套件自带 C6 不替代五个 BLE 身份；首版默认不启用不需要的套件无线、音频和摄像功能，保留 BSP 必需的底层依赖。

刹车 MCU、蜂鸣驱动和保存状态不依赖 P4 页面循环；P4 重启、触摸失效或页面阻塞不能直接停止后台报警。刹车 MCU 本身或其供电故障不具备软件冗余，大屏须将链路/状态未知明确标出，不能宣称整机是冗余报警系统。

### 3.1 两刹车插口的物理总线

现有独立刹车固件使用一条 UART1 RS485 总线、地址 FL=01/FR=02、9600 8N1。本增量建议两个刹车口采用**独立 RS485 收发及 UART**，仍由同一个刹车 C3 管理，以限制单口 A/B 线路故障对另一口的影响。保留原地址作为配置基线；实际每端地址须核准，允许独立 profile 反映真实出厂地址，不自动写传感器地址/参数。

代价是增加一个收发器及更多 GPIO。[ESP32-C3 官方资料](https://documentation.espressif.com/esp32-c3_datasheet_en.html)及本机 SDK 3.3.7 能力定义支持双 UART、原生 USB Serial/JTAG 和 SPI2。双 UART＋SPI 从机含 READY＋蜂鸣需要约 12 个 GPIO，原生 USB 日志另占 GPIO18/19；须核查实际模块、Flash、启动脚及可用引脚。UART0 启动输出期间 RS485 DE 必须保持硬件默认关闭。该控制器优先使用原生 USB 维护日志，不能同时再把 UART0 当作普通日志串口占用。

若不能给选定 C3 模块完成安全引脚分配，实施者在硬件冻结前提出有充足资源的刹车 MCU 修订；不得静默把两口并成总线或挤占原胎温引脚。双总线不等于两套独立 MCU/电源冗余，各路请求、失败重试和恢复仍需分别有界。具体引脚尚未分配。

## 4. 必须继承的刹车行为

依据现有 V1.6 代码，而非仅按旧界面文案移植：

- 两路有效盘温取最大值作为显示温度及**一套共用**热模型输入，保留 `Tfast/Tcore/Dose`。不新增每轮独立阈值或两套模型。Tcore/Dose 显示为模型估算，不能标成测得的制动液/卡钳温度。
- ALM 默认 600°C，范围 100–900°C，步进 10°C。快速滤波、热浸透、Dose、确认保持和解除滞回参数以原 V1.6 为移植基线；参数变化须单独说明和回归。
- ALARM 由 Tcore 持续达到 ALM，或接近 ALM 后满足原辅助确认条件产生；盘面尖峰/Dose 不单独强制 ALARM。
- 有效 ALM 改变时按原行为重置热模型和报警锁存；切页、重复命令或仅保存相同值不得重置模型。设置页说明修改阈值会重新计算报警状态。
- 原状态码 `0 OK/1 WARN/2 ALARM/3 FAIL` 沿用；状态优先级按原判断次序 ALARM→WARN→FAIL→OK，而非按数值取最大。每探头失效标记与全局状态分别呈现。
- ALARM 强制蜂鸣，普通提示音关闭不屏蔽 ALARM；保留 60 秒临时静音，到期仍报警则恢复蜂鸣。WARN 按原提示节奏；当前代码 FAIL 状态本身静音，不在迁移中擅自增加 FAIL 蜂鸣。保留启动蜂鸣及约 3 秒启动保护期。
- 单路失败不发送正常 0°C；两路全失效时模型无效并进入 FAIL。刹车采集过期基线 2500 ms，胎温仍为 1500 ms，不混用。显示通信失效另设状态，不冒充传感器正常。
- 默认采集与 BLE 节奏按原基线规划：约每 100 ms 轮询一路（每测点约 200 ms），BLE 默认约 150 ms 一轮；改为有界非阻塞状态机，不把旧 OLED/按键循环直接塞入 P4 绘制任务。

## 5. 触屏页面与参数归属

### 5.1 页面

- **胎温页**：保留四幅完整 32×24 热图、镜像、共享色标、最高有效温度及状态/年龄；页面导航或报警条不能裁掉测温像素。
- **刹车页**：左右前盘实测温度、有效最大值、ALM、OK/WARN/ALARM/FAIL、各探头在线情况、刹车 BLE 与静音剩余时间；模型详细值标明估算。
- **设置页**：承接原刹车按键功能，包括共用 ALM、普通提示音、60 秒临时静音。胎温 ROI/镜像/滤波继续按原核准配置，首版不因增加设置页而隐含加入胎温运行期 Flash 设置功能。

工程基线：上电默认胎温页；所有页面持续呈现刹车 ALARM 和传感器/控制器失效提示。报警不强制跳走用户页面，可由用户触摸入口查看刹车页。触屏切页不重置模型、不重连 BLE、不停止后台采集；页面切换不是报警的开启/关闭开关。

### 5.2 唯一配置源与保存

刹车 MCU 是配置、报警和保存状态的唯一有效来源。P4 首先读取实际配置及版本，不能以界面默认值覆盖控制器。断开或超期时禁用写入并显示未知；重连先读取真实状态，不自动重放断线前的设置/静音。

工程交互选择：触屏先编辑本地草稿，点击“应用并保存”后提交完整候选配置。该交互替代旧按键“每次调整立即生效、随后保存”的操作方式，防止连续触摸反复写 Flash/重置模型；ALM 范围、报警模型和蜂鸣语义保持。应用成功后才改变有效 ALM 并按需要重置模型；保存失败时保留原有效配置，界面不能提示成功。临时静音使用有意的约 1 秒长按动作，按原行为从首次执行起计 60 秒，不写入 NVS。

命令至少带双方启动/会话标识、唯一序号、预期配置版本和校验。刹车端做范围/版本检查、重复命令去重，回传结果、实际配置、配置版本及已保存状态。ACK 丢失时界面标为待确认/结果未知，通过读回确定，不能声称失败后回滚了实际已保存值；重试不得重复重置模型、写 Flash或延长静音。

NVS 使用版本化完整配置及可恢复提交方案。旧 `brake12v` 配置不得被无提示清除；如复用旧板须在计划中说明迁移/读回，不能静默覆盖用户 ALM。保存中断电和保存期间采集/BLE/蜂鸣的最大停顿需验证，禁止依赖熄火瞬间保存。

## 6. 板间链路与数据有效性

四轮胎温 SPI 快照 v1 保持原 1728 字节、CRC/token、DMA 租约和独立年龄计算。刹车不是第五个胎温轮位，不占用热图保留位或更改既有 WheelId 的 1–4 含义。

工程基线为在同一 SPI 总线上增加第五个从机（刹车控制器），单独定义定长双向 **BrakeLink v1**。P4 需要 3 总线＋5 CS＋5 READY＝13 GPIO，原来四胎温的 11 GPIO 是历史基线。全部五设备由统一非阻塞总线调度管理在途 DMA、互斥与公平性；不能让等待刹车回执阻塞胎温。

BrakeLink 状态包含：控制器启动标识与序号、每路有效位和年龄、原始盘温、有效最大值、模型及有效状态、全局状态与独立故障位、BLE 状态、实际 ALM/提示音、配置/保存版本、静音剩余时间、错误计数和命令回执。控制命令不借用 RaceChrono CAN filter 特征发送。

具体事务长度、偏移、命令枚举、CRC 覆盖、缓存去重和期限由增量计划冻结，再实现编解码。双方不相减绝对时钟；接收状态不等于探头新采样。工程默认将刹车控制链路超过 1000 ms 无有效回传视为显示端未知，传感器自身有效期另按 2500 ms 判定；该显示期限需台架核对。

## 7. RaceChrono 兼容目标

保留四个胎温 RejsaRubberTrac 设备（服务 0x1FF7，三特征各 20 字节）及一个刹车 **N BrakeTemp** 设备（服务 0x1FF8，主特征 0001，filter 特征 0002）。目标手机的五设备共存必须实测，不因同一屏显示就假定已经通过。

下表为旧刹车固件实际布局和新方向的兼容目标，不表示新整机已发送这些通道。DIY CAN 通知前 4 字节为小端 CAN ID，随后是下表 payload；B0/B1 指 payload 内的字节，而非整个通知的前两字节。

| CAN ID | 名称 | payload/单位与缩放 | 计算定义 |
| --- | --- | --- | --- |
| 0x100 | Brake FL | B0–B1，int16 大端，0.1°C/计数 | signed16(B0×256+B1)/10 |
| 0x101 | Brake FR | 同上 | signed16(B0×256+B1)/10 |
| 0x102 | Brake Display | 两路有效最大温度，同上 | signed16(B0×256+B1)/10 |
| 0x103 | Brake Fast | Tfast，同上 | signed16(B0×256+B1)/10 |
| 0x104 | Brake Core | Tcore 估算，同上 | signed16(B0×256+B1)/10 |
| 0x105 | Brake Dose | B0–B1，uint16 大端，Dose×10 | (B0×256+B1)/10 |
| 0x106 | Brake State | B0，uint8，0/1/2/3 | B0 |
| 0x107 | Brake Alarm | B0–B1，uint16 大端，ALM，单位°C，不乘10 | B0×256+B1 |

signed16(x) 表示 x≥32768 时减 65536，否则为 x；这是字节计算定义，不宣称是可以直接粘贴到任意 RaceChrono 版本的函数名。温度 payload=0x7FFF 表示无效，手机端必须排除，不能显示 3276.7°C；Dose/ALM/State 不套用该温度无效值。目标手机计算表达式和失效显示在 BLE 验证中记录。

## 8. 电源、机械、验证与交接

沿用点火供电、无整机续航电池、车载入口保护、显示/逻辑电源及探头支路保护，重新计算六探头、五 C3 和蜂鸣器的启动/峰值电流。电源短路隔离与 RS485 线路隔离分别验收。USB 维护、启动电平、套件 P4/C6 及五 C3 维护接口和天线净空纳入外壳与底板审查，不假设原四口 BOM 或 GPIO 已足够。

在原 A–F 外增加刹车回归：双通道有效/失败与恢复、状态优先级、模型/ALM 改变、ALARM 强制鸣叫与 60 秒静音、P4 重启/触摸失效时后台报警、设置丢包/重复/旧版本/双 MCU 重启、NVS 写入失败及保存中断电、五 BLE 连续共存、两刹车独立线路故障与六路电源保护。全部结果目前未验证。
