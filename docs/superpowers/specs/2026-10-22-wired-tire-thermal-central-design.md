# 四路有线胎温中控设计规格

日期：2026-10-22

状态：整体方案已获用户认可；本书面规格提交审阅，尚未进入实施。

项目代称：四路有线胎温中控。该名称不代表已有硬件版本或稳定固件。

## 1. 使用目标与边界

面向赛道汽车，将四个轮眉胎温探头通过线束接入驾驶舱内的独立中控。中控采用一块定制 PCB，正面固定 7 英寸彩色屏幕，板边提供四个探头插口。显示四轮完整热图，同时通过 BLE 向 RaceChrono Pro 提供各轮的 8 分区胎温。

用户已确认的约束：

- 首版验证采用 YF-RS485-640 成品探头，其内部已包含温度采集 MCU 和 RS485 接口。
- 不采集悬挂高度，不使用轮端电池；车辆点火上电后自动工作，关闭点火后关闭。
- 四个接口分别为 FL、FR、RL、RR；前轮线束约 2 m，后轮约 4.5 m。
- 中控本地必须显示四幅完整 32×24 热图；RaceChrono 保留现有风格的 8 分区热图。
- 一块中控 PCB 集成一个显示主控与四个独立采集/BLE 单元；使用定制板，不将带屏开发套件作为交付结构。
- 保留以后接入自制 RS485 胎温探头的能力。

优先级遵循 AGENTS.md：硬件安全、开机稳定、读取稳定、RaceChrono 连接稳定、抗震抗干扰、低延迟、显示清楚。

成功标准是四轮数据能正确区分、完整热图可见、故障不会被显示或发送为正常温度，并在四路采集、显示和 BLE 同时工作时保持稳定。界面流畅度目标与探头实际采样频率分别验收。

本设计不包含刹车报警、胎压、高度、WiFi 遥测、历史回放或 SD 卡记录。既有胎温高度 v3 和刹车节点仍按原有边界维护；本方案是独立研发方向，不把 v3 改回中控发送版本。

## 3. 总体结构与选型基线

每个轮眉的成品探头，通过独立 RS485 点对点连接，接到中控内对应的采集/BLE 单元。四个单元分别计算 8 分区温度并直接向 RaceChrono 发送；完整温度矩阵通过板内接口交给显示主控。

| 中控 PCB 上的组成 | 职责与依赖 |
| --- | --- |
| 显示主控，基线 ESP32-P4 | 接收完整热图及状态，驱动屏幕，处理显示设置；不承担四个轮位的 BLE 身份 |
| 四个采集/BLE 单元，基线每路一个 ESP32-C3 | 独立 RS485 采集、温度处理、错误恢复、单轮位 BLE 和向显示主控交付数据 |
| 四路 RS485 收发与接口保护 | 各连接一个探头；线路独立，避免单总线轮询的带宽限制 |
| 车载电源及四路支路保护 | 为屏幕、逻辑和探头供电，限制单支路线束故障的影响 |
| 屏幕及机械固定 | 7 英寸 IPS 彩屏，1024×600 作为选型目标；通过板上连接器/排线连接并固定在 PCB 正面 |

P4、C3 是本规格的实施选型基线，尚无新板实测。最终封装、面板、连接器、电源器件、引脚表和 BOM 必须在原理图审查阶段固化，不沿用旧板引脚作为默认接线。P4 不依靠板载 C6 或单个无线端模拟四个轮位。

四个 BLE 天线必须结合外壳、屏幕金属背板及相邻无线单元安排位置，满足所选模块的天线净空要求；集中放在同一外壳后的实际射频表现属于整机验收项。

验证允许使用现成模块搭建台架；交付结构为一块集成 PCB，不能把模块搭建误标为定制板完成。

## 4. 探头与线束接口

| 端口/逻辑轮位 | 轮位编号 | 线长 | 独立物理通道 |
| --- | --- | --- | --- |
| FL 左前 | 1 | 约 2 m | RS485-FL |
| FR 右前 | 2 | 约 2 m | RS485-FR |
| RL 左后 | 3 | 约 4.5 m | RS485-RL |
| RR 右后 | 4 | 约 4.5 m | RS485-RR |

每个接口提供探头电源正、专用电源回线、RS485 A、RS485 B。A/B 使用双绞线；参考地、屏蔽连接、终端匹配、偏置和是否隔离按实际线束及收发器电路审查确定。四个端口不是同一 RS485 总线的四个分支。

接口采用带锁止、防误插的连接形式；针脚编号必须由正式原理图与线束表共同定义，当前仅定义信号，不作为接线施工图。手册列有不同线色组合，装配必须逐个核对实物，不凭颜色推断电源和信号。

四个独立通道允许各探头使用相同 Modbus 地址，例如 `0x01`。轮位由中控端口及对应单元配置决定；Modbus 从站地址不等于轮位编号。换插接口会改变该探头对应的轮位，接线与外壳标识必须一致。

车辆安装需确认视场覆盖胎面，并在转向和悬挂行程内保持线束、探头及支架的机械间隙。探头密封、耐振动、镜头污染及工作环境温度必须实测，手册未提供的车规/IP 等级不得自行宣称。

## 5. 成品探头协议

### 5.1 寄存器与温度解码

手册标称探头供电为 6–29 V，像素温度分辨率 0.1°C。分辨率不代表测温精度。

| 内容 | 寄存器/定义 |
| --- | --- |
| 从站地址 | `0x0000`，手册默认 `0x01` |
| 波特率设置 | `0x0001`，最高列到 115200 bps |
| 停止位设置 | `0x0002`，手册默认 2 位停止位 |
| 内部更新频率 | `0x0005`，列出 0.5/1/2/4 Hz，默认 4 Hz |
| 像素温度 | `0x0010` 至 `0x030F`，共 768 个寄存器 |
| 模块版本 | `0x0310` |
| 普通读取 | `0x03`，手册每次最多 125 个寄存器 |
| 厂商全量读取 | `0x65`，支持超长响应 |

像素按行排列：`index = row × 32 + col`，row 为 0–23，col 为 0–31。每个像素采用有符号 16 位温度计数，`温度°C = 计数 / 10`。寄存器字节顺序按 Modbus 大端解码，CRC 字节顺序低字节在前，均需与实物原始帧对照。

### 5.2 验证基线与手册矛盾

运行配置基线为 115200、8N2；首次接入先识别出厂串口参数，只做读取确认，禁止自动盲写地址、复位或恢复出厂设置。配置修改必须单探头操作、读回并记录，正常上电不重复写配置存储。

以下问题须由台架抓包和热源实验关闭：

1. 波特率默认值在同一表中同时写了 115200 与 9600；探测两者及记录实物停止位后才能配置运行参数。
2. 首页响应频率写 5 Hz，更新频率寄存器最高只列出 4 Hz；本项目以实测新图像响应为准，不承诺 5 Hz。
3. 全量读取例为 `01 65 00 00 03 11 8D 3E`；`0x0311` 表示 785 个寄存器。响应字节数 `0x0622` 等于 1570，手册却写成 1750。须根据实物帧核对长度、寄存器偏移和 CRC，不硬编码错误十进制值。
4. 手册写寄存器的部分例子与地址表不一致，不能直接复制写配置命令。
5. 手册没有证明 `0x65` 返回的是同一时刻的完整快照，也没有定义采样序号；须用移动热源检查帧内一致性。

`0x65` 为厂商扩展，不能交给只支持标准 256 字节 RTU 帧的默认解析器。接收缓冲至少容纳经确认的完整响应，并设置明确上限、长度检查、超时及 CRC 检查。以当前例计算，响应约 1576 字节；115200、8N2 下仅响应传输就约 150 ms，尚不含探头处理和周转时间。四条独立通道可并行接收；不承诺四轮同时曝光。

优先验证 `0x65`。`0x03` 分块读取完整热图至少需 7 次请求；只有确认跨请求数据一致性和性能可接受后才能作为降级模式，不能默默拼接不同采样周期的数据。

## 6. 板内数据与兼容边界

基线采用显示主控作为 SPI 主机，四个采集单元作为独立片选的 SPI 从机。该链路仅在中控 PCB 内使用；具体时钟、握手、DMA 缓冲和引脚分配在台架验证与原理图审查时冻结。

每个采集单元维护最新完整快照。接收中的缓冲与已发布缓冲分离，显示读取不能阻塞 RS485 接收或 BLE。显示只取最新快照，不累积过期帧队列。

板内数据契约包括：

- 协议版本、轮位编号、采集单元启动标识、响应接收序号、有效载荷长度。
- 采集单元本地接收完成时间、读取时数据年龄、通信状态及错误计数。
- `int16` 的 768 个像素温度计数、每像素有效性标记及全帧状态。
- 八个分区温度及各分区有效性、ROI 和镜像配置版本。
- 覆盖头部和数据的完整性校验；编码明确规定字节序，不直接发送编译器内存结构。

SPI 事务期间应读取同一快照；不能将半幅新图和半幅旧图混合发布。采集单元重启后显示必须识别新的启动标识，不能把序号回绕或复位误认为连续数据。

接收序号只代表收到并通过校验的响应，不代表探头发生新采样；两幅相同像素图既可能是静态场景，也可能是重复读取，不能据此判定探头冻结。各 MCU 时钟独立，显示端用本地最后接收时间检测板内超时，不能直接相减两个 MCU 的绝对时间。

未来自制探头可以兼容现有 RS485 协议，也可以增加探头协议驱动；驱动仍向上交付同一套温度矩阵、单位和状态。自制探头的供电范围、接口针脚和协议版本也必须满足接口契约，不能仅凭 RS485 接口就宣称可替换。

## 7. 温度处理与 RaceChrono

### 7.1 温度矩阵到八分区

完整热图使用有效像素的原始温度计数和状态；显示插值只影响绘制，不修改测温数据。RaceChrono 路径参考现有 v3 的处理顺序：有效范围筛选、ROI、trimmed mean、变化率限制、自适应低通、死区、异常跳变保护。

现有参考参数为 32×24、8 行 ROI、8 个横向分区、每区 4 列，ROI 搜索起始行为 3–17，分区温度有效域为 -20 至 200°C。这些是移植基线，不能将其与探头标称 -40 至 300°C 混同；本地完整热图需区分有效温度和分区算法拒绝的范围。

滤波时间参数按实际收到帧的时间间隔计算。由于输入频率明显低于现有快速采集模式，逐帧 ROI 限速和 spike gate 不能未经验证直接照搬；应通过热源移动及静态测试评估延迟与抖动，记录任何参数调整。

轮位、安装方向及镜像设置必须一致：完整热图的方向与八分区对应关系需通过轮胎内/外侧标记验证。某分区无有效温度时，不得以 0°C 填充后当作正常一轮温度发送。

### 7.2 BLE 输出

每个采集单元提供独立 BLE 地址和设备名，RaceChrono 分别添加四个轮位设备。轮位由设备名中的 FL/FR/RL/RR 标识及本地配置共同约束，不能只改一个本地编号就认为 RaceChrono 已识别轮位。

| 项目 | 兼容目标 |
| --- | --- |
| 名称格式 | `RejsaRubber` + `FL/FR/RL/RR` + 稳定的唯一后缀 |
| 服务 | `0x1FF7` |
| 特征 | `0x0001`、`0x0002`、`0x0003` |
| 每特征长度 | 参考现有的 20 字节布局 |
| 温度字段 | B4–B19 为八个 `int16` 小端温度计数，单位 0.1°C |
| 其他字段 | 现有 B0 为 `0x02`；特征 1/3 的 B2–B3 原为高度，特征 2 的 B1、B2–B3 原为电量、电压 |

该方案使用 RejsaRubberTrac 风格 BLE，不是 DIY CAN；不定义 PID/CAN ID。

高度已移除且系统无轮端电池，因此不能把现有高度和电池字段解释成真实测量。实现前的 BLE 兼容验证必须记录这些保留字段的实际编码及 RaceChrono 显示行为；如果需要协议占位值，应明确写成占位，确认不会产生误导的有效测量。完成该项验证后才能冻结新版本的完整 payload 定义。

发送调度以现有约 30 ms 为参考；重复通知不增加探头新采样频率。只在八个分区均有效、数据未超时且 BLE 连接就绪时发送；超时或失败后停止温度通知。必须实测 RaceChrono 如何标记保留的最后值，不能宣称停止通知就会自动清空手机热图。若 RaceChrono 无法明确反映失效，该项作为交付问题解决并记录。

屏幕关闭显示、界面繁忙或显示主控故障时，采集/BLE 单元仍应能独立工作。BLE 断开后重新广播，手机连接/断开不得阻塞采集。

## 8. 屏幕与交互

屏幕为 7 英寸 IPS，目标 1024×600；基线使用 MIPI-DSI。最终面板须同时核对驱动支持、持续绘制能力、可调背光、供电、温度范围、固定结构及驾驶舱日光可读性。普通约 350 cd/m² 开发屏只用于参考，不能据此宣称阳光下可读。触摸功能不是首版必要条件；色标和安装参数可以先通过维护配置设置。

固定四分区：左上 FL、右上 FR、左下 RL、右下 RR。每区包含完整热图、轮位、有效像素最高温度、采集状态和 BLE 状态。传感器故障与手机未连接必须采用不同提示。

四轮使用共同、可配置的温度色标；初始色标和安装方向通过台架/装车配置记录确定，不让四幅图各自自动缩放。无效像素使用独立样式，不能套用正常低温颜色。屏幕只提供配置参考，正式布局需检查数字在实际驾驶距离上的可读性。

界面目标 30 FPS，以双缓冲及同步提交减少撕裂。界面新帧使用最新有效温度，不用时间插值制造额外测温帧，也不增加长时间平滑拖尾。空间放大/插值仅用于改善颜色边缘，不能描述为提高传感器分辨率。

未初始化、传感器超时、板内传输失效的分区灰显并提示明确状态。最近一次热图可保留作参考，但必须标注失效和数据年龄；恢复后只发布通过校验的新数据。

## 9. 供电、复位及现场维护

车辆点火控制的电源开启后系统自动启动，关闭该电源后系统关闭。车上取电点必须验证实际动作：某些附件电源在启动时暂断或熄火后延时断电，不能默认所有 ACC 都与发动机运行状态等价。若所选取电点存在延时供电，应调整取电/使能控制方案以满足用户要求。

电源入口设置保险/限流、反接保护、瞬态抑制及滤波；探头电源经保护后符合其输入范围，屏幕和逻辑分别得到合适电源。6–29 V 是探头的直流范围，不代表已验证汽车浪涌耐受能力。启动压降及供电中断时应稳定复位，不能用无效温度填补欠压期间的数据。

各探头支路短路应限制在该支路内，逻辑及其余探头供电不被拖垮。保护器件、线径、限流值、稳压拓扑和输入测试范围根据实测电流、启动波形及设计环境计算，在原理图审查记录中冻结。

软件不依赖断电瞬间完成必要写入：配置只在明确修改时保存，并保证掉电后可恢复有效配置；正常采集不连续写 Flash。首版不要求电池、用户长按关机或旧 v3 电池电源保持电路。

启动显示主控和采集单元版本、轮位、接口参数、电源状态。保留各轮初始化、CRC/长度/超时错误、恢复次数、有效帧率、BLE 广播/连接/断开/发送状态日志，错误日志节流。为各 MCU 保留可识别的烧录和日志维护通道，故障时能够独立诊断。

## 10. 性能及失败处理

| 情况 | 必须行为 |
| --- | --- |
| 开机未接探头 | 不等待传感器无限阻塞启动；对应区域显示未就绪，后台有界重试 |
| 一路断线、CRC 或长度错误 | 丢弃该响应，不覆盖最后有效快照，不刷新有效时间 |
| 数据过期 | 对应分区失效，停止该轮正常温度通知，其余三轮继续工作 |
| 显示 SPI 事务失败 | 丢弃不完整快照，显示数据超时；采集/BLE 继续运行 |
| 一个采集单元复位 | 显示识别重启，等待其新有效帧；其他轮不重启 |
| BLE 断开 | 单元继续采集和交付热图，恢复广播 |
| 点火电源关闭 | 自动关闭，无需用户操作 |

基线沿用 v3 的 1500 ms 温度过期阈值，后续实测调整须记录。RS485 单次请求、重试间隔与看门狗必须有界；不通过无限重试或长阻塞 delay 隐藏硬件问题。0°C 可能是真实温度，不能仅凭像素为零判定故障；也不能假设通过 CRC 的响应就必然是正常测温，需验证探头自身故障时的输出行为。没有支持采样序号的成品探头，无法仅靠通信成功检测其内部算法冻结，必须如实记录这一限制。

四轮允许不同步采样，界面独立更新各分区。用热源切换录像或外部触发对照测试总延迟；仅记录串口响应时间不能代表从物理温度变化到显示的端到端延迟。

## 11. 验证顺序与放行条件

本节定义后续实施必须取得的证据，不代表本次已运行硬件测试。

| 阶段 | 实验及交付记录 | 放行条件 |
| --- | --- | --- |
| A 单探头协议 | USB-RS485 抓包，记录出厂配置、版本、全帧长度、字节序、CRC；静态/移动热源 | 解码 768 像素，温度与厂商上位机一致；关闭第 5 节的协议矛盾，记录实际更新率、延迟和帧内一致性 |
| B 单轮 BLE | 一个采集/BLE 单元读取探头并向目标手机发送 | 名称/轮位正确，八分区方向和温度正确；明确高度/电池占位以及失效时手机行为 |
| C 四轮 BLE | 四个无线单元在拟用外壳和屏幕后同时运行；四个不同热源依次变化 | RaceChrono 分别连接/记录四轮，无轮位串扰；初步连续 60 min，断开重连可恢复 |
| D 四路显示 | 四路实际探头并行采集，屏幕四区绘制，BLE 同时通知 | 保存界面帧率、各路有效接收率、端到端延迟、最大停顿和错误计数；界面以 30 FPS 为目标，结果未达目标则优化或重新审阅指标 |
| E 线路与电源 | 使用完整 2 m/4.5 m 线束；受控断线、单支路保护测试、反复点火启动及实车用电工况 | 单支路故障不拖垮其余通道；无反复异常复位；关闭点火按要求断电；故障可识别且能恢复 |
| F 车辆安装 | 日光、安装视场、转向/悬挂间隙、振动、温升和实际赛道环境 | 屏幕清楚，线束无机械干涉，热图含义与实际胎面一致，错误及恢复记录可追溯 |

A–C 在正式定制 PCB 投板前完成；不能用四个同名仿真值替代四路真实传感器验证。屏幕和板内链路需在投板前完成接口原型及引脚资源核查，D–F 在集成后继续复测。若任一阶段证明现有探头或 BLE 布局无法满足需求，应报告具体失败证据并修订设计，不能直接改成单个 DIY CAN 设备或降低热图内容。

60 min 为初步台架验证基线，不等于客户交付可靠性认证；交付仍须依据项目现有检查清单和实际使用工况扩大验证。

## 12. 冻结范围与后续产物

本次冻结的是系统分工、四路独立接入、7 英寸同板显示、完整热图与八分区两条数据路径、随点火供电以及独立于旧 v3 的版本边界。

正式硬件选型与引脚表须以验证记录为输入：确认屏幕、供电、收发器、天线布局、连接器、板内握手和 MCU 维护接口，再编制原理图、BOM、线束表及 PCB。具体探头协议参数和 BLE 全部字段的实物验证是这些产物的明确前置条件，不能用本规格推断已有正式引脚或制造文件。

书面规格经用户审阅通过后，再编写实施计划。计划应把协议验证、BLE 兼容、板内传输和屏幕原型列在正式 PCB 和集成固件之前；执行方式由用户审阅计划后选择。本次不提交实施固件、原理图或 BOM。
